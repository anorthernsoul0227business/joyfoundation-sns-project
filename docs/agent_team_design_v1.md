## 2. コンテンツ・ポートフォリオ

認知目的（＝想起されること）に最適化する。実測でイベント告知が突出しているため、
3者案に**イベント・告知型を明示的に追加**する。

| 企画群 | 比率 | 役割 |
|---|---:|---|
| 生活場面・実用体験 | 30% | 初見の人が自分事として入れる入口 |
| **思想・人物・語り** | **25%** | 想起されるのは情報ではなく「声」。競合が構造的に持てない差別化資産 |
| **イベント・告知** | **20%** | **実測で最も到達している型**。日時・締切・固有名詞が効く |
| 活動・現場・実践風景 | 15% | 実在感・安心感（収録現場、企業研修） |
| 研究・根拠の紹介 | **10%** | 信頼の裏打ち。月1回で足りる。note 長文のみ |

**どのカテゴリも0%にしない（下限10%）。** 学習が自分の出力分布を狭め、
反証データが二度と入らなくなるため。調整は月±5〜10ポイントまで。

### エビデンスの位置づけ

> エビデンスは「コンテンツ源」ではなく **ガードレール**。
> EV カードの正しい使い方は「本文に書く材料」ではなく「**書いてはいけないことの辞書**」。（Fable 5）

**「誠実さ」の切り分け:**

- **資産**: 断言しない・押し売りしない・誇張しない**トーン**（全投稿に浸透させる）
- **資産ではない**: 「HF成分に変化はありませんでした」を一般読者向け投稿に書くこと

限界の完全な記述は knowledge/ 層の仕事。投稿の仕事は「断言しないこと」まで。

| 投稿の種類 | 限界の扱い |
|---|---|
| 生活提案 | 断言を避けるだけ（但し書き不要） |
| 思想 | 誰の見解か明示 |
| 研究紹介 | 対象・規模・限界を書く |
| 治療・症状に触れる | 強い検証と明確な注意書き |

## 3. 指標

| | 指標 | 備考 |
|---|---|---|
| **第一** | **フォロワー純増**（両媒体） | 認知の操作的定義＝「次も見たいと思った新規の人の数」 |
| 第二 | IG: 保存率・非フォロワーリーチ比率 / X: プロフィールクリック率 | 「発信者に興味が移ったか」 |
| **見ない** | いいね数の絶対値 | 少数フォロワー期は身内ノイズが支配的 |
| 補助 | インプレッション | アルゴリズム都合で乱高下。認知との相関が弱い |

**測定窓を固定する**: 投稿後 **72時間** と **14日** の2点で取得。
「いつか取った値」は投稿間で比較不能になる。

**想起はプラットフォーム指標では測れない。** 3〜6ヶ月ごとにイベント参加者へ
認知経路を聞く（短いアンケート1問で足りる）。

### ⚠️ 期限のある作業

X の非公開メトリクス（プロフィールクリック等）は**取得可能期間に制限がある（概ね直近30日）**。
X投稿は6/15で止まっているため、**旧53件の詳細メトリクスは一部すでに失われている可能性が高い**。
公開メトリクス（impression_count 等）は残るので、**バックフィルは今週中に実施**すること。

## 4. エージェント構成

### オンライン（週次ループ内・5〜10分で完走すること）

| # | エージェント | 責務 |
|---|---|---|
| 1 | **企画** ★新設 | ポートフォリオ目標＋直近履歴＋adopted INSIGHT＋イベント＋**カードINDEX（タイトルとtopicsのみ。全文は渡さない）** から N本の企画書を出す。企画書＝媒体/切り口/対象読者/使用カード1-2枚/CTA種別/**却下した案と理由**。**重複はここで棄却**（言い換えではなく企画ごと捨てる） |
| 2 | **執筆** | 企画書1本につき、**参照カード1〜2枚の全文＋関連用語だけ**を受け取って書く |
| 3 | 読み手レビュー（ChatGPT/Codex） | 現行のまま。別系統モデルの読み味レビューは正しい設計 |
| 4 | 機械検証 | 現行の `verify()` のまま。**エージェント化しない**（決定論的コードであるべき） |

> 切り口収束（「寝苦しい夜」3連発）の根本原因は、**毎回同じ全部入りプロンプト**。
> `load_recent()` での事後的な重複回避は対症療法。（Fable 5）

### オフライン（一括バッチ・ループ外）

| # | 役割 | 優先度 |
|---|---|---|
| 5 | **カード化エージェント**（残り380件を順次ドラフト化） | **最高**。供給が12枚のままなら1〜4がどれだけ賢くても年内に枯れる |
| 6 | **Voice仕分けエージェント**（協会誌111件→Voiceカード＋リスク三段階 A:SNS可/B:限定/C:発信不可） | 高。思想枠25%の供給源 |
| 7 | 反応収集ジョブ | **スクリプトで足りる。エージェント不要** |
| 8 | 月次振り返りエージェント（INSIGHT仮説レポート生成） | 中 |
| 9 | 修正還元エージェント（圭一郎さんの修正→taxonomy分類候補） | 高（設計済みを動かすだけ） |

### 作ってはいけないエージェント（3者一致）

- **自己改善エージェント**（自分でプロンプトやルールを恒久変更する）
- **バズ担当**（反応最大化だけを担う）
- **自動承認・自動投稿判断**（人のゲートは外さない）
- **LLM検証**（機械検証の置き換え。数値照合・NG表現・文字数・重複検査は決定論的コードで）
- **X用人格 / Instagram用人格**（同じ企画を媒体ごとに表現変換するだけでよい）
- **討論型エージェント群**（賛成役・反対役など責任が曖昧）
- **3体目以降のレビューモデル**（2系統で十分。増やすと遅くなり指摘も重複）
- **リプライ・エンゲージメント自動対応**（認知フェーズで双方向自動化はリスクだけ大きい）
- **トレンド便乗の拡張**（`collect_context.py` の抑制的設計を緩めない）

## 5. 成長ループ: INSIGHT カード方式

**反応データで自動学習させない。** すべての生成挙動の変更を「人が承認した差分」として残す。
既存の knowledge/ 承認アーキテクチャをそのまま流用する。

```
[毎週・機械] 反応収集ジョブ
    Tweet ID / メディアID → API → 「反応データ」タブへ追記（72h / 14d の2窓）
        ↓
[毎月・LLM] 振り返りエージェント（オフライン）
    タグ別集計 → 人が読めるレポート＋仮説候補
    例:「問いかけ導入は保存率が中央値の2.4倍（n=9）。仮説として弱い」
        ↓
[人が承認] 運用担当が仮説の採否を判断
        ↓
knowledge/insights/INSIGHT-0001.md
    仮説 / 根拠（期間・n・数値）/ 適用先 / status: trial→adopted→retired / 検証予定
        ↓
[企画エージェント] adopted の INSIGHT だけを読む
```

**この設計が満たすもの:**

- 生成挙動の変更がすべて git 履歴に残る →「なぜ最近こういう投稿が増えたのか」に必ず答えられる
- 仮説には n と期間と検証予定が必ず付く → 弱い仮説を採用段階で人が落とせる
- 失敗した学習は `status: retired` にするだけ → 巻き戻せる
- EV/RULE カードと同じメンタルモデル → 運用の学習コストがゼロ

**INSIGHT が触ってよいのは企画段階の入力だけ。** 検証段階（NG表現・数値照合）には
一切影響させない、と構造で決める。

### 過学習を避ける4つの構造ルール

1. **学習単位を「投稿」でなく「型」にする** — タグの束に対して集計。個別投稿の成否は学習しない
2. **平均でなく分位で見る** — 判定は「その型の中央値が全体の2倍以上/半分以下、かつ n≥8」程度の粗い閾値。月1回、変更は最大1つ
3. **探索の床** — どのカテゴリも下限10%。0にすると反証データが入らなくなる
4. **最初の問いを間違えない** — 下記参照

### 最初に答えるべき問い（Fable 5 の提案）

手元に**人間が書いた91本という対照群**がある。反応ループが最初に答えるべきは
「どの切り口が伸びるか」ではなく:

> **AI生成パイプラインは、人間の91本に劣っていないか**

これは n=91 vs n=生成分 で答えられる、**数少ない統計的に意味のある問い**。
劣っているなら切り口最適化は時期尚早。

### 時間軸

| 頻度 | やること |
|---|---|
| 毎週 | データ取得・欠損確認・異常検知**のみ** |
| 毎月 | 傾向の記述（「何が起きたか」まで） |
| 3ヶ月 | 企画配分やルール変更の**判断** |
| 半年 | ポートフォリオとブランド認知の見直し |

## 6. 承認フロー

### 前提の訂正

91本をシートで校正できた実績があるため、「シートは使えない」という前回の前提は撤回。
**シートを記録の正とし、圭一郎さんへのインターフェースは本人の既存行動（メール＋音声）に合わせる。**
音声で返ってきた判断を運用担当がシートに転記すればよく、本人に新しいUIを学ばせない。

### カード承認は「投稿経由」に変える（最重要の設計変更）

現在は12枚のEVカードの「解釈承認・公開承認」を求めている（0/12）。**これは失敗する。**
EVカードのレビューは科学論文の読解作業であり、本人が3〜7月に実証した行動（投稿文の校正）とは
別のスキル・別の心理的負荷。

**代替案:**

```
1. 完成投稿文を見せる（カード由来の主張部分をハイライト。週次_内訳に既に分離保存済み）
2. 本人がOKした時点で、使った言い回しを運用担当が AC カード（Approved claim）として切り出す
   ※ schema.md に AC 層が定義済みなのに未使用。ここで使う
3. 以後、同じ AC を使う投稿は A分級＝軽いレビューで通る
4. AC ライブラリが本人の過去のOKから機械的に育ち、レビュー負荷が単調減少する
```

> 「役割を方向性確認に絞る」のは初日に宣言することではなく、**この仕組みの帰結として実現する**。（Fable 5）

**カード単位の事前承認が必要なのは以下だけ:**

- 協会の公式見解として繰り返し使う Voice カード
- 医療・治療・効果に関係する高リスクカード
- 原本と代表指示が食い違う案件（ESC）
- 宇宙軍・予言・政治・陰謀論隣接など、対外的位置づけを変えうる内容

### 判断項目は2問だけ

1. **事実に誤りはないか** — 全文精読ではなく、C分級の `外部情報_要確認` 欄
   （イベント・サービス・実績の主張）だけをチェックリストで提示。
   数値とNG表現は機械検証が担保済みなので、**人が見るべきは機械が原理的に検証できない
   F系（イベント事実）のみ**
2. **協会として出してよいか** — 方向性・ブランドの直感判断

回答は3択: **OK / 直して出す（修正内容）/ 出さない（理由）**
「直して出す」の修正内容が還元ループの燃料になる。

**無応答時のデフォルトは「保留（出さない）」。** 自動公開へのフォールバックは作らない。

### リスク別に見せ方を変える

| リスク | 見せるもの |
|---|---|
| 低 | 本文だけ |
| 中 | 本文＋使用したVoice/Evidenceの要約 |
| 高 | 本文＋原文＋懸念点＋AIが判断できなかった質問 |

## 7. 最も失敗しやすいポイント（3者一致）

> **カード承認0/12のまま、承認ボトルネックが在庫切れを再生産すること。**
>
> 生成ループは動く、検証は動く、投稿機構は動く。しかし `status: active` のカードが0枚なので
> **本番生成可能な投稿は今日時点で0本**。3月の在庫切れは「作り置きが尽きた」だったが、
> 次の在庫切れは「パイプラインは完璧なのに、承認待ち行列の先頭で全てが止まっている」形で起きる。
> しかも**失敗が見えにくい**——システムは毎朝9時に正常稼働のログを吐き続けるから。（Fable 5）

**対策:**

- 承認の単位を本人の実績ある行動（投稿校正）に畳み込む（§6）
- **「圭一郎さんのレビュー滞留日数」をシステムの第一級メトリクスとして毎週見る**

> 成長ループの話を散々したが、このシステムの実効スループットを決める変数は、
> モデルの賢さでもプロンプトでもなく、**この1つの数字**。（Fable 5）

## 8. 実装順序

| # | やること | 根拠 |
|---|---|---|
| **0** | **X メトリクスのバックフィル**（今週中） | 非公開メトリクスに取得期限がある。**期限のある作業** |
| **1** | **7月以降のイベント情報を入れる** | 実測で最も到達している型を、今のループは作れていない |
| **2** | 企画エージェント新設＋全カード一括プロンプトの廃止 | 切り口収束の根治。供給の質が上がる |
| 3 | カード化エージェント（オフライン一括） | 供給の量。年内に枯れないため |
| 4 | 修正還元ループの稼働（設計済み） | 情報密度が最も高い成長軸 |
| 5 | AC カード方式への承認移行 | レビュー負荷が単調減少する構造をつくる |
| 6 | Voice 仕分け（協会誌111件） | 思想枠25%の供給源 |
| 7 | 反応収集ジョブ＋月次振り返り＋INSIGHT | 3ヶ月分たまってから初回の配分見直し |

**やらないこと:** カードの大量増設を承認前に行う（未承認在庫が増えるだけ）／
無制限の連続実行テスト（企画層のない状態での重複を大量生産するだけ）
