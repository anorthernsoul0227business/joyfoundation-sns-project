# SNS Calendar App 設計レビュー（2026-04-16）
## Codex壁打ち結果（全文）

## 前提と総評
- 事業仮説（日本市場、LINE + note差別化、シンプル/プロの二層UX）は妥当。
- ただし、**投稿先API制約（特にInstagram/note/YouTube）と予約実行の信頼性**が事業成否を左右する。
- 最初の6ヶ月は「速度優先」で構築し、ロックインは境界設計（抽象化）で緩和する方針が現実的。

---

## 1) FullCalendar vs react-big-calendar vs schedule-x

### 推奨: FullCalendar + dnd-kit（現案維持）

- 月/週/日/リソース表示・繰り返し・タイムゾーンなどが成熟。
- ドキュメント・実績が最も厚く、運用時の不具合調査がしやすい。
- dnd-kit 併用で「外部カード→カレンダー」などSNS投稿管理に必要なUXを作り込みやすい。
- **リスク**: Premium機能（resource/timeline等）が必要になるとライセンスコスト増。設定が多く初期実装が重くなりやすい。
- **トレードオフ**: react-big-calendarは軽いが高機能化で自作コストが増える。schedule-xは将来性はあるが採用事例と情報量で不利。

## 2) Supabase vs 独自Auth+DB

### 推奨: Supabase Auth + Postgres（RLS前提）で開始、Auth境界を抽象化しておく

- MVP〜PMFまでの速度を最大化。
- App Store公開そのものにSupabase利用は原則問題ない。
- マルチテナント/RLS/監査ログ設計と相性が良い。
- **リスク**: Auth・Storage周辺のロックイン。RLS設計を誤ると情報漏えいリスク。
- **トレードオフ**: 独自Authは柔軟だがセキュリティ責任と開発負荷が急増。

## 3) Celery vs BullMQ vs Supabase Edge Functions

### 推奨: 現時点は Celery + Redis。将来、Node中心化したくなれば BullMQへ段階移行

- 既存Python投稿資産の再利用が最短。
- リトライ、遅延実行、優先度、死活監視など運用知見が豊富。
- AI前処理（要約/生成）を同一実行基盤に寄せやすい。
- **リスク**: 運用要素（worker監視、再実行、重複排除）をきちんと作らないと事故る。
- **トレードオフ**: BullMQはTS統一に強いが既存Python資産の再実装コストが高い。Edge Functionsは軽タスク向き。

## 4) モノレポ vs 分離リポ

### 推奨: モノレポ（apps/web, apps/api, packages/*）

- API型定義・OpenAPIクライアント・デザインシステム共有が容易。
- 変更影響の可視化とCI最適化がしやすい。小規模チームでは運用コストが低い。
- **リスク**: CI設計が雑だとビルド時間が肥大化。
- **トレードオフ**: 分離リポは権限分離しやすいが契約変更の同期コストが増える。

## 5) FastAPI(Python) vs NestJS(TypeScript)

### 推奨: 短中期はFastAPI継続。境界を切って将来一部をNestJS化可能にする。

- 既存X/IGスクリプト流用で最短。AI/データ処理はPythonが依然有利。
- 「投稿実行ドメイン」を独立サービスとして契約固定すれば後移行が可能。
- **リスク**: 二言語運用の認知負荷。
- **トレードオフ**: NestJS統一は採用/教育で利点だが今は速度低下の可能性。

## 6) Claude API vs OpenAI API

### 推奨: 両対応（プロバイダ抽象化）を初期から実装。デフォルト1社+フォールバック1社。

- 品質・コスト・可用性は時期で変動する。
- 日本語ニュアンス、長文要約、構造化出力で優位性が入れ替わる。
- BCP（障害時）と価格交渉力を確保できる。
- **リスク**: 実装複雑性（プロンプト差分、token計測、評価基盤）が増える。
- **トレードオフ**: 単一APIは簡単だが価格/障害/規約変更の単一障害点になる。

## 7) プロンプト管理

### 推奨: ハイブリッド（Git管理YAML + テナント/ユーザー差分はDB）

- 監査性・再現性（Git履歴）と動的変更（DB）を両立。ABテスト・ロールバックが容易。
- **リスク**: バージョン整合（どの投稿がどのprompt_versionか）を記録しないと検証不能。
- **トレードオフ**: ハードコードは最速だが運用破綻しやすい。DBのみはレビュー統制が難しくなる。

## 8) 画像変換タイミング

### 推奨: ハイブリッド（主要サイズはアップロード時先行生成、最終最適化は投稿直前）

- 編集時プレビュー高速化と投稿先仕様変更への追従を両立。
- 投稿失敗時の再実行を軽量化できる。
- **リスク**: ストレージコスト増。変換パイプラインが複雑化。
- **トレードオフ**: 全事前生成は無駄が多い。全オンデマンドは投稿遅延/失敗リスク増。

## 9) note.com対応

### 推奨: フェーズ分割（初期は「下書き補助/コピーモード」、自動投稿は法人契約APIが得られるまで限定提供）

- スクレイピング/Puppeteerによる自動投稿は規約・アカウント凍結・運用保守リスクが大きい。
- App Store審査・法務観点でも説明困難になりやすい。
- **リスク**: UX上「完全自動」で見劣りする可能性。
- **トレードオフ**: 強行自動化は短期訴求になるが長期の事業リスクが高い。

## 10) Web→React Native移行に向けた準備

### 推奨: 今から以下を実施
1. BFF/API契約先行（UIから直接DB依存を避ける）
2. ドメインロジックをpackages化（投稿ルール、バリデーション、状態遷移）
3. デザイントークン導入（Tailwind configをトークンの単一ソース化）
4. フォーム/バリデーション共通化（zodスキーマ共有）
5. 日時処理統一（UTC保存 + 表示時TZ変換）
6. 添付アップロード抽象化（Web/RNで実装差し替え）

### 想定共有率
- ビジネスロジック/型/バリデーション: 60〜80%
- UIコンポーネント: 20〜40%

---

## 優先アクション（実行順）
1. 投稿先ごとの**機能マトリクス**作成（可否、制限、失敗時挙動）
2. 予約投稿の**信頼性設計**（冪等キー、再試行、重複防止、DLQ）
3. 認証/権限の**RLS設計レビュー**
4. LLMの**品質評価基盤**（日本語評価セット、媒体別トーン）
5. note連携の**法務/規約確認**

## 結論
- 現在の提案は方向性が良く、MVPとして現実的。
- ただし「カレンダーUI」よりも先に、**投稿API制約・ジョブ信頼性・規約準拠**を設計の主戦場にするべき。
